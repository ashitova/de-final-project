# Прототип Feature Store для корпоративной платформы машинного обучения
Feature Store, или хранилище признаков, - система для хранения описаний признаков, результатов их расчета и
служебной информации о качестве данных. 
#### Ценность исследования
Использование Feature Store может помочь организовать работу с признаками: 
* избежать дублирования признаков
* сделать более прозрачным механизм расчёта признаков
* упростить доступ к уже рассчитанным признакам
#### Актуальность исследования
На рынке существует уже несколько готовых решения для реализации Feature Store. 
Но часто бывает, что на их изучение нужно потратить много времени, и не факт, 
что предложенное решение будет соответствовать требованиям бизнеса. <br>
Преимущество собственной разработки в том,
что можно учесть все особенности компании: ограничения по использованию ПО, 
особенности организации процессов. И сделать именно то, что отвечает всем требованиям и кастомизациям.
## Компоненты Feature Store
В данном проекте реализовано 4 компонента Feature Store:
1. Offline Store (исторические данные) - реализован на базе Minio (объектное хранилище).
2. Online Store (актуальные данные) - построен на БД ClickHouse.
3. Версионирование и контроль качества/ реестр признаков - реализовано в виде отдельной схемы и таблицы в БД PostgreSQL.
4. Загрузка данных осуществляется из БД PostgreSQL (raw data) в Offline и Online Stores с использованием дагов Apache Airflow.
## Локальная разработка в Docker
Для разработки в докере были подняты образы:
- Minio
- PostgreSQL
- ClickHouse (настройки для этих образов заданы в [docker/docker-compose.yaml](docker/docker-compose.yaml))

скрипт формирует данные и сразу создаёт таблицу в PostgreSQL и загружает в неё эти данные.<br>

Также в данном скрипте создаётся таблица, используемая для ведения реестра признаков (`registry.feature`),

Аналогичный скрипт с инициализацией объектов БД создан для ClickHouse 
(файл [docker/init-scripts/init_clickhouse.sql](docker/init-scripts/init_clickhouse.sql)). 
В нём создаются таблицы, в которые Airflow будет выгружать рассчитанные значения признаков.
## Выгрузка данных
Для выгрузки данных создано 4 дага Airflow (airflow/dags/export_*). 
Логика работы этих дагов одинакова, различаются только признаки, которые они выгружают.
Общий код дагов вынесен в скрипт [airflow/dags/utils/common.py](airflow/dags/utils/common.py). 
Для дагов установлен ежедневный запуск по расписанию (1 раз в сутки).
### Этапы обработки данных в дагах
1. Проверяются подключения к системам: PostgreSQL, ClickHouse, Minio.
2. Проверяется, есть ли в Minio требуемый бакет. Если нет, бакет создаётся.
3. Выполняется запрос (SELECT) в БД PostgreSQL к реестру признаков `registry.feature` 
для извлечения последней версии признака (по дате добавления строки).
3. Выполняется запрос (SELECT) в БД PostgreSQL к таблице `web_analytics` (таблица сырых данных). 
У каждого дага свой запрос - с расчётом требуемого признака.
4. Результаты запроса превращаются в файл parquet.
5. Файл parquet переносится в Minio. Используется следующая иерархия каталогов: 
название признака, версия, дата выполнения запроса. 
Название файла также содержит название признака, версию признака и таймстемп выгрузки.
6. Формируется запрос (INSERT) в БД ClickHouse, старые данные предварительно удаляются, загружаются новые. 
Таблицы в ClickHouse именуются так же, как и признаки. Например, даг export_visits_per_day - признак visits_per_day - 
таблица ClickHouse visits_per_day. В таблицах ClickHouse есть поле для записи версии признака 
(чтобы понимать, каким образом он был рассчитан).
### Показатель посещаемости по датам
Даг [export_visits_per_day.py](airflow/dags/export_visits_per_day.py). Рассчитывается как количество посещений (сессий) 
на дату.
```sql
SELECT DATE_TRUNC('day', visit_datetime) AS visit_date
, COUNT(visit_id ) AS visits 
FROM web_analytics 
GROUP BY visit_date
ORDER BY visit_date
```
Запрос для проверки выгрузки признака в ClickHouse:
```sql
SELECT * FROM analytics.visits_per_day;
```
### Показатель количества просмотра страниц по датам
Даг [export_views_per_day.py](airflow/dags/export_views_per_day.py).
Рассчитывается как суммарное количество просмотров страниц на дату.
```sql
SELECT DATE_TRUNC('day', visit_datetime) AS visit_date
, SUM(page_views ) AS sum_page_views
FROM web_analytics 
GROUP BY visit_date
ORDER BY visit_date
```
Запрос для проверки выгрузки признака в ClickHouse:
```sql
SELECT * FROM analytics.views_per_day;
```
### Показатель отказов (Bounce Rate) по каналам привлечения трафика
Даг [export_bounce_rate_per_source.py](airflow/dags/export_bounce_rate_per_source.py). 
Рассчитывается как процент сессий, 
в которых пользователь просмотрел только 1 страницу и не совершил никаких действий,
группируется по каналам привлечения трафика. Этот признак рассчитан в долях, 
его значения округляются до 4 знаков после запятой и умножаются на 10000, 
чтобы в БД их можно было хранить как целые числа. Соответственно, при использовании этого признака
значения необходимо поделить на 10000 (это указано в комментарии столбца БД).
```sql
SELECT utm_source 
, ROUND(AVG(CASE 
	WHEN page_views = 1
	THEN 1
	ELSE 0
END), 4) * 10000 AS bounce_rate
FROM web_analytics 
GROUP BY utm_source
```
Запрос для проверки выгрузки признака в ClickHouse:
```sql
SELECT * FROM analytics.bounce_rate_per_source;
```
### Показатель средней продолжительности сессии по каналам привлечения трафика
Даг [export_visit_duration_per_source.py](airflow/dags/export_visit_duration_per_source.py).
Рассчитывается как среднее от продолжительности сессий для каждого источника трафика.
```sql
SELECT utm_source 
, ROUND(AVG(visit_duration), 0) AS avg_visit_duration
FROM web_analytics 
GROUP BY utm_source 
```
Запрос для проверки выгрузки признака в ClickHouse:
```sql
SELECT * FROM analytics.visit_duration_per_source;
```
### Обновления реестра признаков
Даг [update_feature_registry.py](airflow/dags/update_feature_registry.py).<br>
Входные параметры: имя и версия признака (feature_name, feature_version). <br>
При запуске этого дага в реестре признаков (таблица `registry.feature` в БД PostgreSQL) 
добавляется запись с указанием новой версии признака. Остальная информация о признаке 
берётся из уже существующей записи реестра, последней по дате создания.<br>
Запрос для проверки загрузки признака в реестр (БД PostgreSQL):
```sql
SELECT * FROM registry.feature;
```
### Сценарий использования
1. Проверить в реестре признаков актуальность указанной по признаку информации.
2. При необходимости обновить данные реестра, запустив даг [update_feature_registry.py](airflow/dags/update_feature_registry.py).
3. Затем запустить даг экспорта признака export_*.
4. Проверить корректность выгрузки, выполнив SELECT данных в БД PostgreSQL и ClickHouse.
5. Проверить наличие файлов в Minio.
6. Данные из ClickHouse можно забирать, например, через sql запросы.
7. Файлы в Minio можно читать через S3 API.
### Выводы
В данном проекте представлен рабочий вариант реализации прототипа Feature Store, 
в котором есть Offline и Online Stores, реестр признаков, 
реализована выгрузка признаков по расписанию с применением оркестратора Apache Airflow. 
В текущее решение можно добавлять как новые источники данных, так и новые признаки. 
Для удобства расширения общие части кода вынесены в отдельный файл и переиспользуются дагами при необходимости.
